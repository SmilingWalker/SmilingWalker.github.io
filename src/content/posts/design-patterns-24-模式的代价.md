二十四篇讲完了二十四种"应该怎么做"。最后一篇讲反面：**什么时候不该做**——这是[第 0 篇](/posts/design-patterns-0-开篇/)登堂入室五层里第 4 层（懂取舍）的毕业考。

## 模式瘾的三种发作

[第 0 篇](/posts/design-patterns-0-开篇/)引过 Coding Horror 的[反思](https://blog.codinghorror.com/rethinking-design-patterns/)，这篇正面展开。模式瘾有三种典型发作，每种都披着"架构升级"的外衣：

**一、简历驱动设计。** "我们引入了事件总线"听起来比"两个服务互相调用"高级。但[第 23 篇](/posts/design-patterns-23-事件总线/)的账单摆在那里：四个坑、一个中间件集群、一套 trace 工具——为两个稳定订阅方付这份钱，买到的不是解耦，是简历上的关键词。**技术的复杂度要和问题的复杂度匹配**，不是和技术人员的野心匹配。

**二、为对称而抽象。** 看到三个结构相似的函数就手痒抽接口，看到两个相似的服务就手痒上模板。但[第 1 篇](/posts/design-patterns-1-策略模式/)的判断标准是"经常加"，不是"长得像"——三个长得像但从不变化的分支，抽成策略是零收益加一层间接。对称是审美，不是需求。

**三、为想象的需求建模。** "以后可能会有第二种支付渠道，先抽象""商家未来可能要扩展，先留钩子"。[第 22 篇](/posts/design-patterns-22-钩子与插件/)说过这是过度设计之王——想象的需求没有形状，为它建的抽象几乎必然猜错方向：第一次接第二家渠道时发现，当初预留的接口漏了签名钩子、多了用不上的方法。**等真实需求来敲门时，它自己会长出正确的形状**——这是全系列"先疼再重构后命名"教学法的另一面：疼没来，别动刀。

## 每个模式的账单（全系列浓缩）

把 23 篇的"代价"栏压成一张总表——**每个模式都在收税，收的是同一种税：间接层**。值得隔段时间重看一遍，加固"付出感"：

| 模式 | 它收你什么（最常见的半句） |
|---|---|
| 策略 | 类型数量膨胀，"选择"逻辑仍需工厂收口 |
| 建造者/FO | 样板代码，每字段一个方法/函数 |
| 单例 | 全局状态污染测试、依赖隐藏 |
| 工厂/注册表 | 按名查找的字符串魔法、注册暗知识 |
| 装饰器 | 层序敏感的调试地狱、大接口转发 |
| 适配器 | 翻译样板、渠道升级全体重考 |
| 外观 | 滑向上帝对象的引力 |
| 桥接 | "正交"判断错了拆成散装 |
| 组合 | 叶子被迫统一的诱惑、深树调试 |
| 代理 | 真实成本被隐藏（穿透三层才知道贵） |
| 观察者/事件总线 | 不可见的调用链、四坑工程 |
| 命令 | 样板翻倍、Undo 语义可能写不出 |
| 状态 | 状态类数量、简单场景的仪式感 |
| 模板方法 | 骨架变更波及全部实现 |
| 责任链 | 长链排障、环间隐式耦合 |
| 依赖注入 | 组装根维护、"不 new"的团队纪律 |
| Repository | 样板层、方法膨胀 |
| 钩子/插件 | 永久 API 承诺、生态养护成本 |

没有免费的模式。**每一个都该在动手前问：这个税，换来的好处我确定要吗？**

## 什么时候丑代码是对的

模式瘾的反面不是无模式，是**承认有些代码就该丑着**：

- **一次性的脚本和迁移工具**：跑完就丢的东西，直接写。给它上策略模式相当于给一次性纸杯雕花。
- **探索期的代码**：新产品连业务方向都在摇摆，抽象锁住的是错误的理解。等业务稳了再抽，[Kerievsky 的顺序](https://refactoring.guru/design-patterns)永远是先有疼后有结构。
- **三次法则（Rule of Three）**：Fowler 在《Refactoring》里提出的经验法则——同样的东西出现第三次，才值得抽象。第一次写，第二次容忍重复（复制是廉价的），第三次抽。前两次的"丑"是付给未来判断力的学费。
- **Rob Pike 的老三样**：a little copying is better than a little dependency（一点复制好过一点依赖）；clear is better than clever；simplicity is prerequisite for reliability。Go 标准库把这三条写进了气质里——`strings.Repeat` 才三行，没人觉得它该抽什么模式。

**丑代码的最高辩护词：它诚实。** 三十个文件里的 switch 是丑的，但它把所有逻辑摊在阳光下；一个猜错方向的抽象是"干净"的，但它把逻辑藏进错误的形状里，让下一个读者要先理解你的误解才能纠正它。**没有抽象好过错误的抽象**——前者加法就能补，后者要先拆地基。

## 模式的真正遗产：不是结构，是三样东西

如果这个系列只留下一件事，我希望是这个：**模式的价值大头根本不在那 23 个结构**。结构在 Go 里还打了折（下节），真正带走的是三样：

**一、词汇表。** "这里建议上装饰器""这坨 if-else 是典型的状态机苗子"——模式名是工程师之间的普通话，一个词省二十分钟画图。没有这套词汇，review 意见只能写成"我觉得这里可以更灵活一点"这种无法执行的话。

**二、力的识别力。** 每个模式背后是一种**力**（[第 0 篇](/posts/design-patterns-0-开篇/)Fowler 的核心概念）：开闭的力、两维变化的力、知情与参与的力、裁决与变换的力。识别出"这段代码在跟什么力较劲"，模式名自然浮现；识别不出，背下 23 个结构也是白背。**力是病，模式是药，系列教的是看懂化验单**。

**三、重构的地图。** "先疼再重构后命名"——模式是重构的目的地，不是设计的起点。Kerievsky 那本书的标题顺序是有讲究的：Refactoring 在前，Patterns 在后。第 1 篇的定价引擎不是"按策略模式设计"出来的，是从三层 if-else 一步步走过去的——**地图上画着终点，但路是一步步 refactor 走的**。

## Go 吃掉的那一半

全系列反复出现一个主题：**Go 替你干了一部分模式**。收官盘点，这是"模式是力不是形"最有力的证据——语言升级了，力少了一些，模式的形状就跟着消失：

| 语言机制 | 吃掉的模式用量 |
|---|---|
| 隐式接口满足 | 半数[适配器](/posts/design-patterns-6-适配器/)（第 6 篇"消费侧定义小接口"） |
| 函数一等公民 | 单方法[策略](/posts/design-patterns-1-策略模式/)、半数[命令](/posts/design-patterns-13-命令/)（闭包即命令对象） |
| `range` / `iter.Seq` | [迭代器](/posts/design-patterns-17-冷门五连/)整个被语言吸收 |
| goroutine + channel | [观察者](/posts/design-patterns-12-观察者/)的 channel 派、[管道](/posts/design-patterns-19-流水线/)的并发形态 |
| 组合 over 继承 | [装饰器](/posts/design-patterns-5-装饰器/)/[桥接](/posts/design-patterns-8-桥接/)从类层次瘦成接口字段 |
| `sync.Once`/泛型 | [单例](/posts/design-patterns-3-单例/)和[注册表](/posts/design-patterns-20-注册表/)的样板 |

所以"Go 程序员要不要学设计模式"的答案是：**要学，但学的比例和 Java 不同**——力全都要学（力是语言无关的），形少学一半（语言替你干了）。这也是为什么全系列每篇都有"Go 特色"一节：那不是装饰，是翻译。

## 从 CloudShop 回望

二十四篇 = 一个系统的完整演化史。最后看一眼这张地图——每行都是从疼出发的，这就是"按问题场景驱动"组织的本意：

| 你遇到的疼 | 去处 |
|---|---|
| if-else 切算法 / 布尔组合爆炸 | 1 策略 / 5 装饰器 |
| 参数爆炸 / 全局唯一 / switch 造对象 | 2 建造者 / 3 单例 / 4 工厂 |
| 接口对不上 / 调用太繁 / 两维变化 | 6 适配器 / 7 外观 / 8 桥接 |
| 树形结构 / 控制访问 | 9 组合 / 10 代理 |
| 状态变了要广播 / 操作要保管 | 12 观察者 / 13 命令 |
| 状态机 / 骨架固定 / 规则排队 | 14 状态 / 15 模板 / 16 责任链 |
| 依赖焊死 / 步骤要插拔 / 按名发现 | 18 注入 / 19 管道 / 20 注册表 |
| SQL 散落 / 不改源码扩展 / 跨服务广播 | 21 仓储 / 22 钩子 / 23 总线 |

CloudShop 的故事讲完了，但它对应的那些真实系统（美团返奖的工厂+策略、投放的责任链、阿里互斥择优的定价、pi 的钩子分层）还在演化。**模式是在真实系统的疼里长出来的，也只在对真实系统的疼里学得会**——GoF 那 23 个结构，本来就是四位作者从各自项目的疼里挖出来的。

## 下一步：不是学更多，是去用

三条具体的路，按顺序走：

1. **重读自测**：把 23 篇的自测题重做一遍（隔了一段时间，做错的那些就是没长牢的）。
2. **在自己代码里找三个疼点**：一段最长的 if-else、一个参数最多的构造函数、一个最不敢动的函数——用对应篇章的 v0→v1 路径走一遍重构。**不写新代码练模式，改自己的旧代码**，收获大一个量级。
3. **读一个真实系统的源码**：`database/sql`（本系列出场最多的包：工厂+注册表+桥接+代理+抽象工厂全在里面）或 client-go（仓储+事件+组合）——用模式的眼睛读，每个文件都会变厚。

学无止境是句客气话，对这个主题的诚实版本是：**24 个模式够用很多年，接下来缺的不是模式，是踩坑的里程数**。

模式是词汇，不是施工图；是地图，不是道路；最好的运用，是读完这个系列后在 code review 里说出的那句——"**这里，先别上模式**"。
